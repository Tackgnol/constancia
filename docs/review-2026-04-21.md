# Code Review — 2026-04-21

Scope: `packages/contracts`, `packages/core`, `packages/systems`, `apps/backend`, `apps/bot`, `apps/frontend` (glance only).
Goal: Identify **block-pattern failures**, **dumb inconsistencies / antipatterns**, **code repetition / monorepo erosion**. No fixes applied — findings only.

---

## 1. Where the Block pattern breaks down

### 1.1 "Block" is an overloaded word
Two unrelated concepts share the name:
- **Pipeline block** — `BlockDefinition`/`BlockInstance` in `packages/contracts/src/block.ts`: a runnable step with `execute(config, ctx)`.
- **NPC system block** — `NpcSystemBlock` in `packages/contracts/src/npc.ts`: a passive data tag (clan, creature-type, stat payload).

They show up side-by-side in `packages/contracts/src/index.ts` and in the Prisma schema (`Event.pipeline`, `Npc.systemBlocks`). There is no shared abstraction — only shared vocabulary. The conflation makes `schemas.ts` confusing (`blockInstanceSchema` vs `npcSystemBlockSchema`), forces duplicate normalizers on the frontend, and will keep costing clarity tax.

### 1.2 The block type contract is not enforced end-to-end
`BlockDefinition<TConfig>` is generic, but the chain that handles a block *loses* that type at every step:

- `packages/core/src/block-registry.ts:4` stores everything as `BlockDefinition<unknown>`.
- `packages/core/src/pipeline-runner.ts:23` calls `block.execute(instance.config, ctx)` where `instance.config` is `Record<string, unknown>`. **No runtime validation against `configSchema` happens** — the JSON schema is declared, never used.
- `apps/backend/src/blocks.ts:32` registers each block with `registry.register(block as never)` — an explicit cast that defeats TypeScript. This contradicts `AGENTS.md` ("`any` strictly forbidden; `unknown` last resort") and signals the generic design isn't pulling its weight.
- `apps/backend/src/blocks.ts:26` emits `block.configSchema as Record<string, unknown>` for downstream Fastify schema composition — another cast around the contract type.

Net effect: a pipeline block whose stored config drifted from its schema (renamed field, wrong shape) will surface as a runtime `TypeError` deep inside `execute`, not a schema violation at the boundary. The "schema-first" design is aspirational, not operational.

### 1.3 Persisted pipeline is untyped
`Event.pipeline` is a `Json` column (`packages/db/prisma/schema.prisma:180`). Every read back into the pipeline runner crosses a trust boundary without validation:

- `apps/backend/src/routes/event-routes.ts:210` — `runner.run(event.pipeline as unknown as BlockInstance[], …)`
- `apps/backend/src/routes/bot-routes.ts:92` — same.
- Same casts for the write side (`event-routes.ts:109, 165`).

`as unknown as X` bypasses precisely the boundary where `AGENTS.md` says narrowing is mandatory. `registeredBlockSchemas` is used for Fastify *input* validation on create/update, but reads from the DB — which is the actual trust boundary with older persisted events after a schema evolution — have no validator.

### 1.4 `outcome-map` emits malformed `player` messages
`packages/core/src/blocks/outcome-map.ts:47-50` builds:

```ts
{ target: 'player', content: outcome.text }   // no targetId
```

But `resolveMessageRecipients` (`packages/contracts/src/block.ts:46-49`) drops any `player` message with no `targetId`. So for the only code path that *actually* fires outcomes to the current player (the natural use case), the bot silently discards them. Either:
- the block should default to `ctx.playerId` (matching `message-player`), or
- the resolver should treat "no targetId" on a player message as "use the invoking player".

Today nobody does the right thing — the messages vanish.

### 1.5 `vtm-pool-resolver` has the same bug + narrower types
`packages/systems/src/vtm-v5/pool-resolver.ts:87-93, 166-168` also emits `target: 'player'` with no `targetId`. Same silent drop. Additionally:

- The return type annotation is `messages: { target: 'player' | 'channel'; content: string }[]` — a hand-rolled narrow type that sidesteps the shared `BlockMessage` union and loses `imageUrl`, `targetId`, `targetIds`.
- `ctx.characterData.attributes as Record<string, number> | undefined` — three `as` casts against `unknown` fields with no guards (`pool-resolver.ts:67-71`). `characterData` is the JSON blob from Prisma and never validated against the system's own `StatSchema`.
- `Math.random()` is used directly — non-seedable, hostile to deterministic tests.

### 1.6 `ctx.playerScore` is a second-class citizen
`BlockContext.playerScore` is optional (`packages/contracts/src/block.ts:60`). `outcome-map` consumes it with `??0`, which quietly turns "no score" into "score 0" and classifies every unrun test as `failure`. The score needs an explicit state ("not yet tested" vs `0`).

### 1.7 `BlockContext.characterData: Record<string, unknown>` is a dead end
Every system-specific block then does its own ad-hoc narrowing (`vtm-pool-resolver` above). There is no mechanism for a system to declare "this is what characterData must look like for my blocks" — the `StatSchema` in `GameSystem` exists but isn't wired to runtime validation.

### 1.8 Block catalogue is maintained in four places
Adding a new block requires touching all of these with zero build-time glue:

1. The implementation (`packages/core/src/blocks/*.ts` or `packages/systems/*`).
2. Registration in `packages/core/src/index.ts` and `packages/systems/src/index.ts`.
3. Backend registry assembly in `apps/backend/src/blocks.ts`.
4. Frontend's **parallel** schema + labels + defaults in `apps/frontend/app/lib/event-schema.ts` (see §3.1).

No test ensures these stay in sync. Drop a block from step 4 and the frontend editor silently can't build it.

### 1.9 Block `configSchema` is JSONSchema7 but validation is Fastify-only
- Core blocks author `configSchema: JSONSchema7`.
- Backend uses those schemas to compose a `blockInstanceSchema` (`apps/backend/src/schemas.ts:301`).
- Frontend re-derives everything in Zod (`apps/frontend/app/lib/event-schema.ts:20-68`).
- The pipeline runner never validates.
- The bot's `/send-messages` receiver uses Zod (`sendMessagesPayloadSchema`) — but only for the delivery payload, not blocks.

Three validation dialects (JSONSchema, Fastify-compiled JSONSchema, Zod) for one concept.

### 1.10 `conditional-gate` semantics are implicit
`conditionalGateBlock` halts the pipeline when the predicate fails (`blocks/conditional-gate.ts:50`). That's a surprising side-effect for a block whose name suggests "gate" (i.e. branching, not halting). There's no config knob — pipelines mix "gate" (halt-on-false) with `outcome-map.shortCircuit` (a different knob doing a different thing) with `EventPipeline.shortCircuit` (yet another meaning at the event level). The three "short-circuit"s need to be named differently or consolidated.

## 1a. Fixing the Block pattern

One-to-one with §1. Each suggestion is independent; take them in any order.

### → 1.1  Rename one of the two "blocks"
Keep `Block` for the pipeline concept (the runtime-flavoured one). Rename the NPC concept — `NpcTrait`, `NpcAttribute`, `NpcDossierField`. Touch points: `packages/contracts/src/npc.ts`, `apps/backend/src/schemas.ts` (`npcSystemBlockSchema`), Prisma column `Npc.systemBlocks` (use `@map` to keep the DB column name, rename only the Prisma field), both `generated/` trees after OpenAPI regen. No behavior change; the name itself prevents future confusion.

### → 1.2  Make `BlockDefinition<TConfig>` earn its generic
Introduce a Zod (or JSONSchema + Ajv-compiled) validator as a first-class field on the block:

```ts
export interface BlockDefinition<TConfig> {
  type: string;
  label: string;
  configSchema: z.ZodType<TConfig>;      // single source; JSONSchema derived
  execute: (config: TConfig, ctx: BlockContext) => Promise<BlockResult>;
}
```

Then:
- `BlockRegistry.register` stays typed; drop `as never` in `apps/backend/src/blocks.ts:32`.
- `PipelineRunner.run` calls `block.configSchema.parse(instance.config)` before `execute`, surfacing a `BlockConfigError` with `{ blockType, instanceIndex, zodIssues }`.
- Export JSONSchema for Fastify via `zod-to-json-schema` (one helper, replaces the hand-built `blockInstanceSchema` in `schemas.ts:301`).

Net: one schema source, runtime validation at the call site, no casts.

### → 1.3  Validate the persisted pipeline at the DB boundary
Add a `parsePipeline(json: Prisma.JsonValue): BlockInstance[]` helper that runs `z.array(blockInstanceSchema).parse(...)`. Use it in **every** place that currently writes `as unknown as BlockInstance[]` (`event-routes.ts:210`, `bot-routes.ts:92`). On parse failure: log + 500 for reads, 400 for writes. This catches schema drift from older rows the day a block's config shape changes, instead of deep inside `execute`.

Optional follow-up: a `scripts/validate-events.ts` job that loads every `Event.pipeline` and reports drift — cheap to write once §1.2 lands.

### → 1.4  Fix `outcome-map`'s silent player-message drop
Two options, pick one project-wide so everyone knows the rule:

- **A (preferred):** the pipeline runner injects `ctx.playerId` as the default `targetId` whenever a block emits `{ target: 'player' }` without one. Done in `packages/core/src/pipeline-runner.ts` right after `block.execute(...)`, so every system-level block inherits the behavior. `resolveMessageRecipients` can then keep its strict "drop if no target" stance.
- **B:** teach `resolveMessageRecipients` to fall back to "the invoking player" — but that requires threading `ctx.playerId` into the bot, which currently only sees `SendMessagesPayload`. More plumbing for the same outcome.

Either way, add a regression test: `outcomeMapBlock.execute(..., { playerId: 'P1', playerScore: 5 })` must produce a message that resolves to `P1`.

### → 1.5  Harden `vtm-pool-resolver`
Three independent fixes:

1. **Type its inputs.** Define a `VtmCharacterData` Zod schema in `packages/systems/src/vtm-v5/character.ts` (`{ attributes: Record<string, number>; skills: Record<string, number>; hunger: number }`) and call `.parse(ctx.characterData)` at entry. Removes all three `as` casts on lines 67–71.
2. **Use the shared `BlockMessage` type** for the return value instead of the hand-rolled narrow shape on lines 63–66. It'll surface `imageUrl`/`targetId` support for free.
3. **Inject randomness.** Add an optional `rng?: () => number` to `BlockContext` (or a narrower `ExecutionContext` the runner builds from `BlockContext` + services). Default to `Math.random` in the runner; tests pass a seedable PRNG. Extracts the non-determinism out of every system block.

### → 1.6  Give `playerScore` an explicit "not tested" state
Options in increasing order of effort:

- **Narrowest:** `outcomeMapBlock` refuses to run when `ctx.playerScore === undefined` — halts the pipeline with a clear error instead of silently treating it as `0`. A pre-test `conditional` can gate it.
- **Medium:** add an explicit `ctx.testResult?: { score: number; outcome: string }` shape populated only by resolver blocks (`vtm-pool-resolver`, future Mörk Borg resolver). `playerScore` deprecated. `outcome-map` reads `ctx.testResult.score`.
- **Widest:** blocks declare dependencies (`requires: ['testResult']`) and the runner refuses to execute an `outcome-map` in a pipeline without an upstream resolver. Best long-term, most scaffolding.

Pick one; document the contract in `packages/contracts/src/block.ts`.

### → 1.7  Wire `StatSchema` into runtime character validation
Today `GameSystem.statSchema` is declared but only consumed by the UI. Make it enforceable:

- Give each `GameSystem` a `parseCharacterData: (input: unknown) => TCharacterData` method.
- On character create/update (`character-routes.ts`), resolve the campaign's `gameSystemId` → system → parse `systemData` before handing to Prisma. Rejects malformed input at the API boundary.
- `BlockContext.characterData` becomes `TCharacterData` (generic), resolved per-system when the runner is constructed for an event.

This also kills the `as Record<string, unknown>` in `bot-routes.ts:97`.

### → 1.8  Make the block catalogue single-sourced
Today block knowledge lives in four places (implementation, `core/index.ts`, `backend/blocks.ts`, `frontend/event-schema.ts`). Collapse to one:

- **Option A (minimal):** Have each block export itself; `packages/core/src/blocks/index.ts` re-exports a `coreBlocks: readonly BlockDefinition[]` array. Same for `packages/systems`. Backend imports the arrays and registers them in a loop. Delete the hand list in `apps/backend/src/blocks.ts`.
- **Option B (the big win):** Create a new `packages/block-catalogue` (browser-safe, no `execute`) that exports `{ type, label, configSchema (JSONSchema), defaults }` per block. Consumed by:
  - `packages/core` to build its runtime `BlockDefinition` (adds `execute`).
  - `apps/frontend` to power the editor — replaces `BLOCK_TYPES`, `BLOCK_LABELS`, `defaultBlockConfigs`, Zod schemas (all derived via `json-schema-to-zod`).
  - `apps/backend` for Fastify schema assembly.

Add a catalogue-sync test: for every entry in `coreBlocks`, assert the backend registry contains it. Prevents silent drops.

### → 1.9  Collapse the three validation dialects
Choose Zod as the authoring format (it's already in the repo for `blockMessageSchema`). Derive JSONSchema for Fastify and Orval via `zod-to-json-schema`. Delete the hand-written `blockMessagePlayerSchema`/`blockMessageChannelSchema`/`blockMessageGroupSchema` in `schemas.ts:643-680` — they duplicate the Zod union in `packages/contracts/src/block.ts:4-22`. One authoring format, two emitters.

### → 1.10  Disentangle the three "short-circuits"
Name them distinctly and document in `packages/contracts/src/block.ts`:

- `EventPipeline.stopOnHalt` (replaces `EventPipeline.shortCircuit`): runner behavior when any block returns `halt: true`.
- `ConditionalGateConfig.onFalse: 'halt' | 'skip-next' | 'continue'`: explicit, discoverable, default `'halt'`. Drops the current surprise that "conditional-gate" halts.
- `OutcomeMapConfig.mode: 'bucket' | 'cumulative'`: replaces `shortCircuit?: boolean`. `'bucket'` (default) = exactly one outcome whose `[min, max]` contains the score; `'cumulative'` = every outcome with `min ≤ score`. The current flag's polarity is backwards and its default is undocumented.

Each block rename is a contract change — gate on regenerating OpenAPI clients (§3.2) in the same PR.

## 2. Dumb inconsistencies & antipatterns

### 2.1 `any` is banned, but casts are everywhere
`AGENTS.md` says `any` is forbidden and `unknown` is a last resort to be narrowed immediately. Live code in direct violation:

| File | Line | Cast |
|---|---|---|
| `apps/backend/src/blocks.ts` | 32 | `register(block as never)` |
| `apps/backend/src/blocks.ts` | 26 | `configSchema as Record<string, unknown>` |
| `apps/backend/src/routes/event-routes.ts` | 109, 165, 210 | `pipeline as unknown as …` |
| `apps/backend/src/routes/event-routes.ts` | 163 | `status as EventStatus` (no runtime guard) |
| `apps/backend/src/routes/bot-routes.ts` | 92, 97, 156 | `pipeline as unknown as …`, `systemData … as Record<string, unknown>`, `'ready' as EventStatus` |
| `apps/backend/src/routes/character-routes.ts` | 98, 160 | `systemData as Prisma.InputJsonValue` |
| `apps/backend/src/routes/campaign-npc-routes.ts` | 238 | payload `as Prisma.InputJsonValue` |
| `packages/systems/src/vtm-v5/pool-resolver.ts` | 67–71 | `as Record<string, number>`, `as number \| undefined` |

### 2.2 P2025 is re-discovered in every route
Seven files detect Prisma's "record not found" with the exact same boilerplate (`apps/backend/src/routes/*`, 11 occurrences):

```ts
if (typeof err === 'object' && err !== null && 'code' in err
    && (err as { code: unknown }).code === 'P2025') { … }
```

This belongs in one helper (e.g. `isNotFound(err)`) or a Fastify error hook.

### 2.3 Response envelope is hand-written 48 times
`{ status: 'ok', data: … }` / `{ status: 'error', data: { message } }` is typed out in 48 places across 9 route files (see `grep "status: 'ok'"`). Two consequences:
- There is no single source of truth for the envelope shape — `standardResponseSchema` is defined in `schemas.ts` but only used via the wrappers `singleResponseSchema` / `listResponseSchema`.
- Error shapes diverge subtly. `channel-routes.ts:156` returns `{ status: 'ok', deleted: false }` for a missing channel; `bot-routes.ts:307` returns `404 { status: 'error', data: { message } }` for a missing participant. Same conceptual event, different API shapes.

### 2.4 Per-route param/body interfaces duplicate the JSON schemas
Every route declares TypeScript `interface FooBody { … }` beside a `fooBodySchema` in `schemas.ts` containing the same fields. They drift silently — `eventPatchBodySchema` allows any `status: string`, while `EventPatchBody.status` is just `string`, while the DB column is `EventStatus` enum. No coupling, three sources of truth.

### 2.5 Silent enum narrowing
- `event-routes.ts:163` casts a user-supplied string directly to `EventStatus` with no validation — `PATCH /events/:id { status: "garbage" }` will hit Prisma, which *will* error, but from Fastify's point of view the body was valid.
- `eventPatchBodySchema.status` is `{ type: 'string' }` with no `enum` list. The DB, the Prisma type, and the runtime all know the four valid statuses — only the public contract doesn't.
- Similarly `gameEventSchema.status` is unrestricted.

### 2.6 Validation inconsistency: bot's HTTP server vs backend
- Backend uses Fastify JSON schema validation (config-schema-first).
- Bot's `/send-messages` uses Zod (`sendMessagesPayloadSchema.safeParse`). It even registers no Fastify schema, only a manual parse in the handler — which skips Fastify's standard error response shape.
- Same repo, two validation stacks, two error response shapes.

### 2.7 `normalizeRecipientIds` diverges by location
Four implementations:
1. `packages/core/src/blocks/message-player.ts:3-16` — accepts `string | string[] | undefined`, splits strings by `,`.
2. `packages/core/src/blocks/message-group.ts:3-16` — identical to #1 (literal copy/paste).
3. `apps/frontend/app/lib/event-schema.ts:5-15` — **only** accepts arrays; no string-splitting path.
4. `apps/frontend/app/components/recipient-multi-value-field.tsx` — yet another variant (checked by grep, not read).

A user typing `"a,b,c"` in the frontend gets a single-ID array; the same value passes through the backend's copy and gets split. Behavior differs by path.

### 2.8 `Math.random()` in game logic
`vtm-v5/pool-resolver.ts:21` rolls with `Math.random()`. No seeding, no injection point, no test harness. Any future test that wants to assert dice outcomes has to mock the global.

### 2.9 Error handling mostly `console.*` + swallow
`apps/backend/src/services/bot-client.ts` and `apps/bot/src/http-server.ts` use `console.error/warn/info` directly instead of the Fastify request logger in scope. `interaction-router.ts` does the same.

### 2.10 `as const` response wrappers leak Fastify types oddly
`listResponseSchema` / `singleResponseSchema` (`schemas.ts:787-807`) lose `additionalProperties` (not `false`), so every response allows extra keys through, contrary to every body schema.

### 2.11 `standardResponseSchema` is dead code
Declared at `schemas.ts:404` but not imported anywhere. Clear sign the envelope is handled ad hoc.

### 2.12 Two ways to pass bot headers
- `apps/bot/src/api/bot-headers.ts` just re-exports `botRequestOptions` from `../config.js`.
- That's a pointless hop — the file exists (per git status as a recently added indirection) but does nothing.

### 2.13 `npcBodySchema` allows `value: {}` (i.e. anything)
`schemas.ts:220` types NPC block `value` as `{}` (no type). Combined with `additionalProperties: false` on the outer object, it means "any valid JSON of any shape". Contract says `NpcSystemBlockValue` is a recursive JSON, but the schema doesn't encode that at all — so the DB accepts `undefined`, functions, etc., if callers constructed them via the TypeScript interface, with no runtime check.

### 2.14 Root `dependencies` include `better-sqlite3` and `kysely`
`package.json:40-42`. The stack is Postgres + Prisma (`schema.prisma:6-8`). Neither sqlite nor Kysely is referenced by the apps. `AGENTS.md` notes `better-sqlite3` only as an upstream transitive dep — having it at the repo root is a leftover / trap. `kysely` has no call site.

### 2.15 VTM `outcome-map.shortCircuit === false` semantics
`packages/core/src/blocks/outcome-map.ts:41-45` — when `shortCircuit` is **omitted**, it filters by `[minScore, maxScore]`; when `false` it filters by `minScore` alone (stacked outcomes). That's the opposite of what "short circuit" usually means, *and* the absence of the flag behaves the same as `shortCircuit: true`. A user reading the schema (`{ shortCircuit: boolean }`) cannot infer the default.

### 2.16 Channel `DELETE` success ≠ bot participant `DELETE` success
- `channel-routes.ts:149-158` on missing row: `200 { deleted: false }` (not in `deleteResponseSchema` idea of failure).
- `bot-routes.ts:306-326` on missing row: `404`.
Same verb, same concept, different contract. Pick one.

### 2.17 Event status state machine is implicit
There's no validation that a `ready → fired` transition is legal, that a `fired` event can't be reset to `draft`, etc. `PATCH /events/:id` will set status to whatever string you like (after §2.5 is fixed). The `fire` endpoint doesn't even change status — `event-routes.ts:208-242` runs the pipeline and returns, leaving `status` untouched. So the DESIGN.md "fired dims at 35%" UX requirement has no backend signal yet.

## 3. Monorepo structure breakdown

### 3.1 `event-schema.ts` is a shadow catalogue of blocks
`apps/frontend/app/lib/event-schema.ts` re-declares:
- `BLOCK_TYPES` (an 8-element array, hand-curated).
- `BLOCK_LABELS` (hand-curated strings).
- Zod config schemas for every block type.
- `defaultBlockConfigs` — default config for the form.
- `pipelineBlockConfigNormalizers` — per-block normalization on submit.

Contrast with `packages/core`, which already owns `block.type`, `block.label`, and `block.configSchema`. The frontend cannot currently *import from* `@constancia/core` without dragging block runtime code into the browser bundle — but there's no `@constancia/contracts`-style shared "block metadata" export either. Result: **the frontend editor's block list is a manually-maintained fork of `apps/backend/src/blocks.ts`**.

This is the single largest monorepo boundary failure. Fix candidates:
- Split block metadata (type, label, configSchema, defaults) into a browser-safe package.
- Derive the frontend Zod schemas from the core JSONSchema (via `json-schema-to-zod` or similar).
- Or: drive the frontend purely from the OpenAPI `blockInstanceSchema.anyOf`.

### 3.2 Two `generated/` client trees from one OpenAPI spec
`apps/bot/src/api/generated/` and `apps/frontend/app/api/generated/` both contain full copies of every endpoint module (auth, bot, campaigns, channels, characters, events, journal, meta, npcs, systems). Orval runs twice with `clean: true`.

Practical issues:
- Regeneration is noisy in git (see current `git status` — massive modified generated-file churn).
- Bot imports non-bot endpoints it doesn't use (characters, journal, etc.) and ships them.
- One OpenAPI change → two regenerated trees need to land atomically; easy to get out of sync (see `AGENTS.md` "Orval client regeneration after channel routes were added").

### 3.3 Hand-rolled API calls inside the generated tree
`apps/bot/src/api/participants.ts` is a hand-written fetch client living next to the generated one, with its own env-var read (`process.env.BACKEND_URL`) and its own request types. Its comment says it's temporary "until the OpenAPI spec is regenerated" — but the file will rot there until someone notices. The generated client already knows about `/bot/sync-participants` in recent routes.

### 3.4 `apps/bot/src/delivery/resolve-message-recipients.ts` is a one-line re-export
```ts
export { resolveMessageRecipients, type ResolvedMessageRecipients } from '@constancia/contracts';
```
Either inline at the import site or delete the file. Its existence suggests there *was* a bot-local implementation that was moved; the wrapper kept the old import path alive, and now it's a layer that does nothing.

### 3.5 `bot-headers.ts` is the same kind of empty wrapper
`apps/bot/src/api/bot-headers.ts` = `export { botRequestOptions } from '../config.js';`. Zero added value.

### 3.6 `blockMessage` schemas exist twice (Zod + JSONSchema)
- Zod: `packages/contracts/src/block.ts:4-22`.
- JSONSchema: `apps/backend/src/schemas.ts:643-680`.
They have to match by hand. The backend uses its JSONSchema for Fastify response validation; the bot uses the Zod version for its `/send-messages` input. No single source.

### 3.7 NPC "systemBlocks" normalizer lives where blocks don't
`normalizeNpcSystemBlocks` + `toNpcSystemBlocksInput` + `isRecord` sit in `apps/backend/src/routes/campaign-npc-routes.ts:198-239`. They're the only runtime guard on `NpcSystemBlockValue`. If any second consumer appears (the frontend reads NPC blocks from the API, for instance), the guard needs to move — currently it's hidden inside route code.

### 3.8 Backend routes handle bot-facing and user-facing concerns in one file
`apps/backend/src/routes/bot-routes.ts` has both low-trust bot traffic (setup, participant sync) *and* the pipeline execution entrypoint for player rolls. That's a large surface behind a single `x-bot-key`. Splitting "bot operational" from "bot test-result" would make policy (rate limits, logging, auth strength) easier to tune per concern.

### 3.9 `campaign-npc-routes.ts` handles both privileged and player-facing GET endpoints via `publicMode`
The plugin registers a completely different route set at `/public/campaigns/:id/npcs` (player-safe) vs `/campaigns/:id/npcs` (GM-privileged) by switching on `options.publicMode` (`campaign-npc-routes.ts:354-408`). Two personas in one plugin module. Two plugins would keep auth concerns and response shapes cleanly separated; today they share a types file and the branching is just an `if` near the top.

### 3.10 `packages/systems/src/mork-borg` is an empty stub
Only `data.ts` exists with NPC block declarations; no `pool-resolver`, no `GameSystem` implementation. `getNpcSystemBlockDefinitions` returns the MB blocks anyway, so the UI will offer them while the backend has no runtime behaviour. Partial delivery.

### 3.11 DB types leak into route-level TypeScript interfaces
Routes import `Prisma`, `EventStatus`, `ChannelType` from `@constancia/db` and use them directly in request/response interfaces (e.g. `ChannelBody.type: ChannelType` in `channel-routes.ts:27`). Per `AGENTS.md`: "`packages/db`: Prisma schema. Isolated, ONLY the backend imports it." — that rule is respected, but the type leak means every API-shape change is coupled to a DB schema change. The contracts package already owns `ChannelType` (`packages/contracts/src/campaign.ts`) — the route should depend on that, not on the Prisma enum.

### 3.12 Generated files are in-tree and heavily churned by git
The current `git status` shows ~25 generated files modified — any PR that touches OpenAPI will tangle with hand edits. Considerations: move generated output to an ignored directory and regenerate in CI, or vendor with a clear "DO NOT EDIT" header + pre-commit check.

## 4. Frontend block representation — scan + feasibility

### 4.1 What "block UI" looks like today

Three files carry the entire frontend block surface:

- `apps/frontend/app/lib/event-schema.ts` — catalogue: `BLOCK_TYPES`, `BLOCK_LABELS`, `defaultBlockConfigs`, per-block Zod schema, `pipelineBlockConfigNormalizers`.
- `apps/frontend/app/components/pipeline-builder.tsx` — the outer list (add/remove/reorder, block-type picker). Iterates `BLOCK_TYPES`.
- `apps/frontend/app/components/block-config-fields.tsx` — **one function, one giant `if`-chain with 8 branches**, each hand-rolling the form fields for that block's config. Nested `OperatorSelect` and `OutcomeMapConfig` components live in the same file.

There is **no** view-side block representation:
- `routes/play.tsx:73-76` calls `fireEvent(...)` and discards the response body entirely (`await fireEvent(...)` — no `const result =`). The `{ messages, halted }` payload never reaches the UI, so the Play View shows no pipeline echo, no per-block outcome, no evidence of what fired. The DESIGN.md "Fired" state styling is implemented at the trigger-card level only (local `firedItems` set), with no link to what the pipeline actually emitted.
- `routes/log.tsx` is entirely hardcoded mock data — no real timeline, no block outputs.

### 4.2 What "add a block" costs today

To add a new pipeline block on the frontend (assuming BE/core already have it), a contributor must edit **6 places minimum** across 2 files:

1. `BLOCK_TYPES` tuple — event-schema.ts:72
2. `BLOCK_LABELS` record — event-schema.ts:85
3. Per-block Zod schema — event-schema.ts:20-68
4. `defaultBlockConfigs` record — event-schema.ts:96
5. A new `if (blockType === 'x') return (...)` branch — block-config-fields.tsx
6. Optionally `pipelineBlockConfigNormalizers` for pre-submit cleanup — event-schema.ts:127

This is the exact opposite shape from the backend (`apps/backend/src/blocks.ts` — one array push), and from the bot (which doesn't enumerate block types at all — it consumes the shared `BlockMessage` union). The frontend is the only layer where "add a block" is an open-ended refactor instead of a one-line registration.

### 4.3 Specific smells in the current layer

- `block-config-fields.tsx:260-265` — two `as never` casts to shoehorn `useFormContext` into a dynamic field path. Symptom of the typed form schema not knowing about discriminated-union blocks.
- `block-config-fields.tsx:286` — `control: control as any` with an eslint-disable comment. Same root cause.
- `block-config-fields.tsx:67-70` — `errors.pipeline?.[index]?.config ?? {}) as Record<string, { message?: string }>` — error type is erased because the pipeline field-array is typed as `unknown config`.
- `pipeline-builder.tsx:50` — `const currentType = pipelineValues?.[index]?.blockType as BlockType | undefined` — mirror of the above. The form values are `config: Record<string, unknown>`, so everything downstream has to re-narrow.
- `pipelineBlockSchema` in `event-schema.ts:109-112` uses `z.record(z.string(), z.unknown())` for `config` — i.e., the frontend never validates a specific block's config during the form submit step. The per-block Zod schemas exist but are not wired into the discriminated union that RHF resolves against. So validation errors you *see* come from `eventFormSchema`'s outer shape, not from the specific block shape.
- `normalizeRecipientIds` is a third re-implementation (see §2.7) with different semantics from the core and frontend form-level versions. Three branches of the same function live in the same app.
- The `PipelineBuilder` has no reorder affordance in the visible JSX — add/remove only. If DnD reordering is planned for the "war-room" aesthetic, it would land in this file as a fourth concern mixed with add/remove/type-select.
- Orphaned `apps/frontend/src/` directory contains an unused re-export (`export {}`) plus a stale generated `api/` tree. Dead code living under a sibling of the real app root confuses grep and IDE navigation.
- `apps/frontend/packages/systems/` is a stub with one empty file. It looks like a half-started attempt at a **frontend-local** per-system package (for the UI-only bits of a system module). If the intent is "systems have frontend assets", the existing top-level `packages/systems` should host them.

### 4.4 Target shape — a Block UI Plugin module

To match the backend's modularity, each block should own its own UI the same way it owns its own `execute`. Proposed shape (one per block, co-located):

```ts
// packages/block-catalogue/src/message-player/index.tsx (browser-safe)
export const messagePlayerUi: BlockUiPlugin<MessagePlayerConfig> = {
  type: 'message-player',
  label: 'Message Player',
  configSchema: messagePlayerConfigSchema,    // Zod; shared with runtime
  defaults: { content: '', playerIds: [] },

  // Edit mode — pluggable form fields
  EditFields: ({ pathPrefix }) => <MessagePlayerFields pathPrefix={pathPrefix} />,

  // View modes — shown in play-echo / log / pipeline preview
  Summary:    ({ config }) => <SummaryRow>Sends to {config.playerIds?.length ?? 'triggering player'}</SummaryRow>,
  OutcomeCard:({ config, result, messages }) => <PipelineEchoCard … />,

  // Optional submit-time normalizer (replaces pipelineBlockConfigNormalizers)
  normalize: (config) => ({ ...config, playerIds: cleanIds(config.playerIds) }),
};
```

Then the top-level components become registry-driven:

```tsx
// pipeline-builder.tsx
{registry.list().map(({ type, label }) => <SelectItem value={type}>{label}</SelectItem>)}

// block-config-fields.tsx collapses to:
const plugin = registry.get(blockType);
return <plugin.EditFields pathPrefix={`pipeline.${index}.config`} />;
```

Registry implementation is ~40 lines (Map + register + list). Mirrors `BlockRegistry` in `packages/core` almost verbatim — same mental model as the runtime side.

### 4.5 Three "views" of a block + what each needs

| View | Where | What it shows | Needs |
|---|---|---|---|
| **Edit** | `routes/setup.tsx` pipeline editor | Config form for the block | `EditFields` + `configSchema` + `defaults` |
| **Summary** | `setup.tsx` list row, `play.tsx` event preview | One-liner describing what the block will do (e.g. "DM Aleksei 'The door opens'") | `Summary(config, warRoomContext)` |
| **Outcome** | `play.tsx` post-fire echo, `log.tsx` timeline | What the block actually produced — dice, messages delivered/skipped, whether it halted | `OutcomeCard(config, result, messages)` — needs backend work (§4.7) |

The Edit view is 95% of what exists today. Summary + Outcome are the gap.

### 4.6 Per-system UI composition

`packages/systems/src/vtm-v5/pool-resolver.ts` ships a runtime block. Its frontend fields (`block-config-fields.tsx:225-252`) live *in the app*, not with the system. Applying §4.4 consistently:

- `packages/block-catalogue/src/core/*` — UI plugins for the 7 core blocks.
- `packages/block-catalogue/src/vtm-v5/*` — UI plugin for `vtm-pool-resolver`, co-located with its runtime definition in `packages/systems/src/vtm-v5/`.
- Frontend boots by calling `registry.registerAll([...coreBlocks, ...systemsForCampaign(id)])`, exactly the shape the backend already uses.

This means Mörk Borg (today a stub) can land as a single PR that adds `packages/systems/src/mork-borg/` runtime + `packages/block-catalogue/src/mork-borg/` UI — no touching of any central frontend file. Backend gets the runtime register; frontend picks up the UI register automatically.

### 4.7 Backend work this needs

Two API extensions that block the "Outcome" view from being possible at all:

1. **Per-block outputs in the fire response.** Today `fireEvent` returns `{ eventId, messages, halted }`. To render an outcome card per block, the response needs `blockOutputs: Array<{ blockType: string; output: unknown; messages: BlockMessage[]; haltedHere: boolean }>`. The `PipelineRunner` already has `outputs: unknown[]` internally (`packages/core/src/pipeline-runner.ts:5`) — currently flattened away. Preserve and expose it.
2. **Stable block instance identity.** To tie an outcome back to its edit-time row, block instances need ids (`BlockInstance.id`). Currently `BlockInstance = { blockType, config }`, so two `message-channel` blocks are indistinguishable on return. Adding `id` is a one-line contract change with a migration for existing pipelines (generate ids on load if missing).

Both are prerequisites — the frontend can't do the Outcome view without them. They belong in the same roadmap epic as the UI registry.

### 4.8 Feasibility assessment

**Import constraints** (cleanest news): `packages/core`'s block modules are pure TS (`Math.random`, plain object manipulation — no Node APIs, no Prisma imports). They are already browser-safe. A browser-safe `packages/block-catalogue` can import block metadata directly from `packages/core` and `packages/systems`; only the Prisma-touching backend wiring has to stay in `apps/backend`.

**Schema bridge**: block `configSchema` is currently JSONSchema7. Frontend needs Zod. Three paths, in descending order of preference:

- **A. Switch core to Zod as the authoring format.** Derive JSONSchema for Fastify via `zod-to-json-schema`. One source of truth. ~100 LoC change across 8 blocks, mostly mechanical.
- **B. Keep JSONSchema, generate Zod.** Use `json-schema-to-zod` at build time. Adds a build step but preserves the current authoring style.
- **C. Dual-write (current).** Leave both in place, accept drift. Rejected — see §1.2.

**RHF integration**: `react-hook-form` + `zodResolver` supports `z.discriminatedUnion('blockType', [...blockUnions])` natively. Once each block exports its Zod schema, `eventFormSchema.pipeline` becomes an array of that union, errors become properly typed per-branch, and the `as any` / `as never` casts in `block-config-fields.tsx` all disappear. This is the single biggest correctness improvement on the frontend side.

**Render-time plugin loading**: the UI registry is built once at app boot (no SSR-dynamic concerns since the catalogue is static per system). No code-splitting needed at first; if bundle size becomes a concern per campaign's system, split at `systemsForCampaign(id)` boundary.

**Effort estimate (no surprises):**

| Scope | Effort | Outcome |
|---|---|---|
| **S** — collapse `BlockConfigFields`' 8 branches into per-block files + a registry (same JSX, same Zod, just files). | 1–2 days | `block-config-fields.tsx` becomes `<plugin.EditFields>`, `pipeline-builder.tsx` unchanged, `event-schema.ts` split. No new features. Removes the `as any`/`as never` holdouts if the discriminated union lands. |
| **M** — new `packages/block-catalogue` (browser-safe), single-sourced metadata shared with backend, Zod as authoring format. | 3–5 days | "Add a block" becomes one module in one package. Backend registration is a `registerAll(catalogue)` loop. Frontend is a mirror. Drop `BLOCK_TYPES`/`BLOCK_LABELS`/`defaultBlockConfigs`. |
| **L** — Summary + Outcome view plugins, backend `blockOutputs` response, `BlockInstance.id`, Play View pipeline echo panel, Log View driven by real data. | 1–2 weeks | Delivers the DESIGN.md "command echo" + "fired-dim-with-trace" UX. Each new block automatically shows up in all three views. |

**Risk concentration**: the M tier is the load-bearing one. If M lands well, L is additive and incremental; if M is skipped, L will re-fork the catalogue shape for a third time.

**Recommendation (if asked)**: ship M as one focused PR after §1.2 (Zod-as-authoring) lands — they're the same change touching two packages. Then L can be done one block at a time without churn. S-tier alone is tempting but leaves the multi-location catalogue in place, so the "add a block" experience barely improves.
